# Architecture

- `apps/web`: Next.js web entry point, with Tailwind and configuration ready for shadcn/ui components.
- `apps/vscode`: VS Code extension host, local workspace snapshot adapter, analysis worker and Explorer webview.
- `packages/shared`: versioned, framework-independent snapshot and analysis contracts.
- `packages/core`: snapshot-in, result-out analysis engine; no filesystem fetching, browser, React, Next.js, or VS Code dependencies.
- `packages/github`: server-side public GitHub snapshot acquisition adapter with fixed API endpoints and bounded resources.
- `packages/graph-ui`: reusable React Flow architecture map, graph adapter and ELK layout; independent of Next.js and repository acquisition.

Both clients will supply snapshots to the same core and render its results. Acquisition and presentation stay outside the engine. Package exports point at generated JavaScript and declarations; Turbo builds dependencies before dependent checks and builds.

## Analysis pipeline

`analyzeSnapshot(snapshot, options?)` validates the version 1.0 snapshot before analysis. Invalid schema, entries, IDs, duplicate normalized paths, absolute paths, backslashes, traversal, unsupported extensions, or limits throw `SnapshotValidationError`. Inputs contain `.ts`, `.tsx`, `.js`, `.jsx`, and `tsconfig.json` / `jsconfig.json` only. Paths use POSIX separators; redundant `.` and separators are normalized. Defaults are 10,000 files, 2 MiB per file, and 50 MiB total UTF-8 content; callers can lower or raise them with `maxFiles`, `maxFileBytes`, and `maxTotalBytes`. Files are sorted, indexed in memory and parsed once with the TypeScript Compiler API. Syntax diagnostics retain one-based, end-exclusive locations; analysis continues across parse errors.

The resolver uses TypeScript's module resolution against an in-memory host containing only snapshot files and directories. It supports relative extension and index lookup, TypeScript extension substitution, and the nearest snapshot `tsconfig.json` or `jsconfig.json` compiler options including `baseUrl` and `paths`. Configuration parsing errors are diagnostics. Configuration inheritance and project references are not followed and produce warnings. Default resolution uses Node10 conventions; supplied resolution options can alter behavior. No host filesystem is consulted.

Edges point **from importer to dependency**. Each source file is `file:<normalized path>`; external packages use `package:<package name>` (subpaths aggregate to the package). Edge IDs contain the encoded importer path, source offset, kind, and target ID. They are deterministic for identical source text, but edits before a reference can change its edge ID. Nodes, edges, and diagnostics are sorted. Each edge records kind, original specifier, location, and evidence. Shared types add these fields optionally for compatibility with 1.0 consumers; this engine always supplies them. File IDs from the input validate snapshot identity but do not determine graph identities.

Static imports, re-exports, literal dynamic imports and literal `require` calls are captured. Missing relative or matched alias targets and nonliteral calls are diagnostics without edges. Bare specifiers not matching an alias are modeled as external packages, not verified as installed; unresolved package subpaths and package exports cannot be established without package metadata. Dynamic expressions, require shadowing, semantic/type errors, package manifests, and config inheritance are not modeled. The UI-flow graph returned by `analyzeSnapshot` remains a placeholder; use the separate UI-flow API below. Confidence reflects syntactic evidence, not proof of runtime behavior. Further resolution modes and incremental caches can be added behind the snapshot boundary.

## Web shell

The web app owns route composition, design primitives, repository URL validation, and Explorer interaction state. The bundled example and the separate App Router fixture are analyzed at the server module boundary. In development, public imports are acquired once and analyzed in a bounded worker in the acquisition route; production acquisition is disabled until distributed protection is integrated. the snapshot, both analysis results, and completeness diagnostics are retained together in the browser tab session. Switching modes does not repeat analysis. Impact and Learning modes consume the same session and its existing graphs.

## Architecture map

`@codedna/graph-ui` adapts `DependencyGraph` into React Flow elements without changing node or edge IDs, importer-to-dependency direction, or source metadata. File and external package nodes have different treatments; counts represent immediate incoming and outgoing edges. The Explorer owns one selected graph ID. File-list selection and graph selection update it, and the inspector shows source for files or context for packages. The map highlights the selected node and its immediate incoming and outgoing neighbors; clicking the canvas clears selection.

ELK's layered left-to-right layout receives sorted IDs and fixed node dimensions. It runs asynchronously, ignores stale completions, and falls back to a deterministic non-overlapping grid on failure. Selection changes do not relayout. The canvas offers pan, zoom, fit and reset. A warning appears at 250 nodes and React Flow limits rendering to visible elements; data is not truncated. Layout runs on the browser's main thread, so large or dense graphs can still pause interaction; a worker and incremental layout are future improvements. Edge routes are React Flow paths based on laid-out node positions rather than ELK's routed edge sections. The bundled ELK layout test covers a 500-file chain, not every topology.

Analysis diagnostics remain visible above the map. Empty graphs, single files, cycles, and disconnected components are supported. Repository acquisition remains separate from graph presentation.

## Public GitHub acquisition

`POST /api/repositories/acquire` accepts JSON `{ "url": "https://github.com/owner/repo" }`. URLs must be canonical HTTPS GitHub repository URLs without a trailing slash, `.git`, credentials, port, query, fragment, encoded components, or extra path segments. The adapter lowercases owner and repository names. The landing form invokes this endpoint and opens the resulting session in Explorer.

The server-only adapter reads public repository metadata and resolves the default branch to a commit and its tree SHA. It requests the recursive Git tree, then fetches eligible blobs by SHA using fixed `api.github.com` URLs and no redirects. Each blob's size and Git SHA-1 are verified. GitHub's tree response can be truncated; the adapter fails instead of returning an apparently complete snapshot. No repository code is cloned or executed. A GitHub token is optional via the server-only `GITHUB_TOKEN` environment variable; for fine-grained tokens, public repository Contents read access is sufficient. Metadata is checked for public visibility even when a token can access private repositories. Never expose the token through a `NEXT_PUBLIC_` variable.

Only `.ts`, `.tsx`, `.js`, `.jsx`, `tsconfig.json`, and `jsconfig.json` are acquired. Dependency and generated directories (`node_modules`, `.git`, `.next`, `.turbo`, `dist`, `build`, `coverage`, `vendor`, `.output`, and `out`) and `.min`/`.bundle` source files are excluded by policy. Binary or invalid UTF-8 source entries, symbolic links, and submodules are skipped with diagnostics and `completeness.complete: false`; no files inside submodules are fetched. Configuration inheritance, package manifests, Git LFS resolution and GitHub-hosted dependency contents are not acquired. Git LFS pointer files are not expanded and are reported as skipped. Results are complete only relative to these documented filters, not a byte-for-byte copy of the repository.

Defaults cap acquisition at 1,000 files, 2 MiB per file, 50 MiB total source, 1,003 API requests, four concurrent requests, and 30 seconds. Options can lower these bounds; the adapter also has hard upper bounds. The API limits request body size to 4 KiB and concurrent acquisitions to two per server process. This is not a distributed rate limiter or abuse protection: public deployment needs gateway-level rate limiting and request-body timeouts. GitHub unauthenticated rate limits are shared and can be reached well before the adapter request limit.

Successful responses contain the normalized repository identity, commit SHA, snapshot, acquisition diagnostics, completeness metadata, and both analysis results, with `Cache-Control: no-store`. Errors are sanitized: malformed input is 400, unavailable/private repositories 404, rate limiting 429, size limits 413, truncated trees 422, GitHub failures 502, timeout 504, and busy server 503. Missing blobs are hard failures. Client cancellation aborts in-flight requests. No token, stack trace, source logs, or arbitrary response URLs are returned. See GitHub's [Git trees](https://docs.github.com/en/rest/git/trees) and [Git blobs](https://docs.github.com/en/rest/git/blobs) documentation for endpoint behavior.

## Static UI-flow analysis

`analyzeUIFlows(snapshot, options?, adapter?)` validates the same `RepositorySnapshot` and returns `{ graph, diagnostics, framework? }`. It is separate from `analyzeSnapshot`, preserving its existing dependency and placeholder UI-flow behavior. `UIFlowFrameworkAdapter` receives a validated snapshot, an indexed file map and cached TypeScript `SourceFile` parser. Automatic selection recognizes used Expo Router value imports inside a route root and React Router route declarations backed by imports. Next.js page conventions retain priority unless Expo evidence is present without Next.js source imports; a project with both Next.js page conventions and Next.js source imports takes priority over Expo. Expo takes priority over React Router, which takes priority over React Navigation. A recognized React Navigation factory call is required as source evidence. Multiple framework evidence produces a diagnostic; `nextAppRouterAdapter`, `expoRouterAdapter`, `reactRouterAdapter` and `reactNavigationAdapter` can be selected explicitly without loading framework runtimes. With no Expo evidence, existing Next.js and React Router selection is unchanged. Additional framework adapters can use the same interface without modifying dependency analysis. The two public analysis calls currently have separate parse caches; each file is parsed at most once within one UI-flow call.

The Next.js adapter recognizes `app/` or `src/app/` page files, including a single app root at any repository depth. When multiple candidate roots are found, analysis reports ambiguity instead of merging applications; callers can pass `{ appRoot: "path/to/app" }` to `analyzeUIFlows` to select one exact discovered root. The Explorer does not yet offer a root selector. Discovery uses file paths and may identify unrelated directories named `app` as candidates; it does not inspect package manifests or prove framework installation. It removes route groups, preserves dynamic, catch-all and optional catch-all pattern names, and records inherited `layout`, `loading`, and `error` files as metadata. If both roots exist it chooses `app/` and emits a warning. Parallel slots and intercepting routes are recognized and reported as unsupported rather than treated as ordinary screens. Equivalent dynamic patterns, route groups resolving to the same path, and optional-catch-all conflicts produce collision diagnostics and cannot be navigation targets. IDs are `screen:<source path>`, and locations are one-based and end-exclusive. Convention detection is heuristic: a snapshot without package metadata cannot prove that a project uses Next.js.

Navigation detection looks for imported `next/link` default components and named `next/navigation` hooks or redirects inside a statically identified exported page component. A directly imported, directly rendered component is attributed only when a single page uses it and no other relative importer is visible; shared or indirect cases are diagnostic and unattributed. Attribution records the component location and lower confidence, and does not prove runtime execution or reachability. It does not traverse transitive component rendering, resolve aliases for component attribution, model namespace/re-export imports, or perform type or control-flow analysis. Shadowed imported identifiers are conservatively ignored, and JSX spread attributes make the href dynamic.

`navigationEvents` describes all supported detected actions, including external URLs, dynamic expressions, unresolved or ambiguous destinations and history-based `back`. Only a uniquely matched internal route receives a source-to-target `UIFlowEdge`; unresolved events do not invent target nodes. Literal absolute paths are matched to known route patterns with static segments preferred; relative hrefs, object hrefs, computed expressions, and framework behavior such as rewrites, middleware, conditional routes, base paths and locale prefixes are not resolved. A resolved edge is static evidence of a possible action, not a reachability claim. Unsupported syntax, nonliteral navigation, ambiguous attribution and parse errors produce localized diagnostics. The example snapshot and actual graph output are in `packages/core/fixtures/next-app-router.snapshot.json` and `docs/examples/next-app-router-ui-flow.json`.

## UI Flow map and session lifecycle

`UIFlowMap` in `@codedna/graph-ui` adapts only actual `UIFlowGraph.nodes` and `.edges` to React Flow. The adapter preserves IDs, direction and source metadata; `navigationEvents` never become visual edges. ELK uses the shared deterministic layered layout and fallback grid. The map marks dynamic patterns and source diagnostics, highlights immediate neighbors, and supports pan, zoom, fit, reset and keyboard selection. It warns for 250 or more screens and renders only visible elements at that threshold; ELK still runs on the main thread. An empty state distinguishes absence of supported framework evidence from a detected framework without modeled screens. Framework detection is based on source evidence and conventions; it does not prove which runtime is installed.

Explorer retains independent Architecture and UI Flow selections. Selecting a screen highlights its source file and opens an inspector with route, framework, incoming edges, detected outgoing events, resolution, location, evidence and an optional source preview. Unattributed events, diagnostics and partial acquisition details remain separately visible. Mode switching does not rerun either analyzer.

The GitHub flow stores one acquired snapshot and both analysis results in `sessionStorage` for the current browser tab. The session is reused on reload and carries the pinned revision, avoiding re-analysis while browsing. It is not a persistent repository cache and does not deduplicate repeated imports. Browser quota is typically much smaller than the server's acquisition limit; oversized imports fail with a visible message. Closing the tab discards the session. The server acquisition endpoint still needs deployment-level distributed rate limiting and body timeouts. The App Router example can be opened at `/explorer?example=next`; it is the same snapshot used by the core fixture.

### React Router adapter

The React Router adapter recognizes named imports from `react-router` and `react-router-dom` and statically declared JSX `Routes`/`Route`, `createRoutesFromElements`, and `createBrowserRouter` arrays (including local constant arrays). Literal nested paths, index routes, pathless layouts, `:parameter` and `*` patterns are mapped; parent routes with children are treated as layouts, so only leaf routes are screens. Route IDs contain the declaration path and source offset, stable for identical input but subject to change when preceding text changes. Relative component imports resolve against snapshot files; local or directly imported function/variable components are attributed when their implementation is statically visible. Layout components and unresolved imports are not assumed to be screens.

Named `Link`, `NavLink`, `Navigate`, `useNavigate`, and route loader/action `redirect`, `redirectDocument` and `replace` calls produce source-located events. Absolute and statically resolvable route-relative destinations are matched against route patterns, with static paths preferred. Relative `..` removes a contributing route level, rather than a URL segment. Relative destinations from parameterized or wildcard source routes remain unresolved. Numeric `navigate` calls are history events without a destination. External, dynamic, unresolved and ambiguous actions do not create edges. Components reached through statically named JSX references are grouped by route ownership; shared component actions stay unattributed. This is syntactic evidence, not proof that the component rendered or the action executed.

Unsupported dynamic arrays, spreads, paths, import aliases beyond relative component paths, namespace imports, re-exports, lazy components, object-form destinations, relative-mode options, optional segments and runtime route generation are not modeled. Parent layout navigation is not attributed to child screens. Colliding route patterns are reported and cannot resolve to a unique target; unrelated routes continue to be analyzed. Source offsets and component ownership can change after edits. The analyzer does not inspect package manifests or use a React Router installation. See the official [routing conventions](https://reactrouter.com/start/declarative/routing), [route element conversion](https://reactrouter.com/api/utils/createRoutesFromElements), and [navigation API](https://api.reactrouter.com/v7/functions/react-router.useNavigate).

### Expo Router adapter

The Expo adapter recognizes used value imports such as `Stack`, `Link`, `router`, or `useRouter` from `expo-router` inside `app/` or `src/app/`. No package manifest or Expo runtime is required. It prefers `src/app/` when both roots exist and reports the conflict. Default-exported function screens map file paths to public paths: `index` is omitted, route groups are removed, and `[id]` and `[...slug]` are retained. `_layout` files are inherited layout metadata rather than screens. Screen IDs are `screen:expo:<source path>` and are stable while the path remains unchanged. Colliding group or parameter patterns are diagnosed and cannot be resolved as navigation targets. Files without an identifiable default function, special `+` conventions, unsupported groups, declaration files and test files are excluded or diagnosed.

Static `Link` and `Redirect` hrefs, the imported `router` object and `useRouter()` bindings produce source-located events for `push`, `replace`, `navigate`, and `back`. `navigate` has its own navigation kind because Expo may push or unwind the stack. Back is an unresolved history event. Unique internal targets become source-to-target edges; dynamic values, external URLs, ambiguous targets and history do not. Directly rendered local imports are attributed only when a single screen owns them and no other importers exist; shared navigation is retained as unattributed evidence. Layout navigation is not assigned to every child screen.

Relative links are resolved using document-relative semantics only for static, unambiguous source paths; nested index routes, dynamic source paths, route-relative options and unsupported href objects remain unresolved. Platform-specific screen/layout variants are diagnosed and excluded; if a base screen has variants, its actions are kept unattributed, since the active implementation depends on the platform. Platform-specific imported components are also treated as ambiguous. Re-exported screen components, custom route roots, group-qualified destinations, shared array groups, generated routes, aliases for component imports, namespace imports, native deep-link configuration and runtime routing are not modeled. See Expo's [file notation](https://docs.expo.dev/router/basics/notation/), [navigation](https://docs.expo.dev/router/basics/navigation/) and [platform-specific routing](https://docs.expo.dev/router/advanced/platform-specific-modules/).

### React Navigation adapter

The React Navigation adapter recognizes named factory imports and calls from `@react-navigation/native-stack`, `@react-navigation/stack`, `@react-navigation/bottom-tabs` and `@react-navigation/drawer`. It supports literal JSX `Navigator`/`Screen` registrations and literal static `screens` objects, including literal static groups. The navigator identity combines its source file and declared variable; each screen ID combines that identity, the screen name and registration offset. IDs are deterministic for the same source, but edits before a registration can change its ID. Nodes expose optional navigator identity, kind, group and parent IDs; they use screen names rather than URL paths. Screen source is associated only when a local or directly imported function or common named re-export can be resolved from the snapshot.

A registered component that statically renders one recognized navigator establishes a parent-child relationship. Navigation resolves a literal screen name in the current navigator first, then in a uniquely known parent. A literal `navigate('Parent', { screen: 'Child' })` can target a uniquely known child navigator screen; its optional `navigationPath` records both names. A navigator registration without an explicit child target has no inferred destination. Duplicate names within one navigator, multiple possible parents, dynamic registrations, unsupported nested parameters and unresolved components receive diagnostics rather than guessed targets. Recognized destructured screen `navigation` props and imported `useNavigation()` bindings supply source-located `navigate`, `push`, `replace`, `goBack` and unresolved `reset` events. Actions in components registered or directly rendered by multiple screens remain unattributed. Back and reset never invent a destination.

The adapter does not model namespace imports, higher-order/lazy components, arbitrary component aliases, `props.navigation`, navigation refs, dynamic screen factories, route configuration computed across modules, static screen helper calls, deep nested navigation parameters, conditional navigator mounting, or runtime state. It does not prove that a registration is mounted or that navigation occurs. Source-only analysis cannot resolve hidden importers or dynamically constructed hierarchies; explicit adapter selection is useful when several frameworks coexist. See React Navigation's [screen registration](https://reactnavigation.org/docs/screen/) and [nested navigators](https://reactnavigation.org/docs/nesting-navigators/) documentation.

## Impact analysis

`createImpactAnalyzer(result, options)` builds a reusable reverse adjacency index over the existing dependency graph; `analyzeImpact(result, filePath, options)` is the one-shot convenience API. The browser imports the separate `@codedna/core/impact` entry point, avoiding the parser dependency in the client bundle. Dependency edges point from importer to dependency, so breadth-first traversal follows incoming edges from the changed file. The selected file has distance zero; distance one is a direct dependent, and greater distances are transitive dependents. Cycle detection and visited distances prevent repeated traversal. A bounded number of shortest importer-to-dependency paths retains original edge IDs and source evidence. Results are deterministic for identical graph data.

A source-evidenced path means every retained dependency edge has full confidence and source evidence; it does not mean the dependent will break or execute. Missing evidence is marked uncertain. Dependency diagnostics, UI-flow diagnostics, invalid graph edges, partial snapshots, traversal limits and path limits are reported; at most 50 source diagnostics of each type are displayed, with an explicit omitted count. Source diagnostics may indicate relationships missing from the graph, so even an apparently complete traversal cannot guarantee all impact is found. Unknown or configuration files not represented as file nodes produce an empty result and diagnostic.

Screens are included only when their `sourceFile` matches the selected or reverse-reachable file. Their UI-flow evidence and dependency paths are preserved. This is a direct static source association and possible impact, not proof of execution. Navigation graph edges are never traversed as code dependencies. Shared or unassigned UI-flow attribution can omit screens; UI-flow diagnostics are surfaced when supplied.

Defaults cap traversal at 1,000 files, 30 dependency steps and three shortest paths per file; callers can configure these limits. The Explorer builds the reverse index once per active analysis and recomputes only the bounded traversal on selection. The impact graph contains the retained path edges, with original importer-to-dependency arrows. At 250 files it initially shows the complete list and requires an explicit request to run ELK layout, which still runs on the main thread. The list and graph are not silently truncated, but the traversal limits can omit results and are reported.

### Next.js ESLint warning

The root `eslint.config.mjs` configures ESLint and TypeScript ESLint, but does not register `@next/next`; the Next.js build's lint check detects this and emits its plugin warning. The plugin is not installed in the current workspace. Lint and build still run, but Next-specific lint rules are absent. Adding a plugin would require a dependency and compatibility evaluation against this workspace's ESLint 10 and Next.js 15 versions, so this phase leaves the existing configuration unchanged.

## Learning Mode

`generateLearningPlan(result, uiFlowGraph?, options?)` consumes existing dependency and UI-flow graphs; it neither parses nor executes source. The separate `@codedna/core/learning` export lets the browser generate a plan without importing the TypeScript parser. Lessons have stable kind-based IDs and include an objective, an action, bounded file references, evidence and relative complexity. Empty or partial input produces explicit warnings, and unavailable lesson types are skipped.

The plan begins with source-extension and top-level-folder counts. Files named `index`, `main`, `app`, `page` or `_layout` are possible entry, route or layout candidates; this is a filename heuristic, not proof of an entry point. A connected-module lesson ranks files by distinct incoming plus outgoing internal neighbors, breaking ties by stable file ID, and lists available dependencies before the selected module and its importers. Degree is not business importance. Paths containing `util`, `utils`, `service`, `services` or `lib` are optional reading hints, not claims about their responsibilities. A UI lesson uses an attributed source screen and, where available, an actual evidence-bearing navigation edge. An impact lesson uses a recorded dependency edge in the reverse-change direction. Cycles and disconnected files do not require a topological ordering.

The default limit is six files per lesson and three questions, with at most seven lessons and two currently implemented questions. A dependency lesson is labeled advanced when more than three representative edges are shown; otherwise it is moderate. Evidence-bearing navigation and impact lessons are moderate, and overview, entry and recap are introductory. These labels describe the amount of static material presented, not developer skill or runtime complexity.

Knowledge checks use only source-evidenced edges. An importer question requires exactly one distinct direct importer and two non-importing file choices; a navigation question requires a single detected source for a uniquely labeled target and two uniquely labeled distractors. Ambiguous cases are omitted. Answers and explanations cite the underlying edge evidence; a correct answer only describes the available static graph, not reachability or runtime behavior. Diagnostics and partial acquisition can mean the graph is incomplete.

The Explorer keeps the current lesson, completed IDs and selected answers in component memory while switching modes. Its key includes source, repository identity, snapshot ID and revision, so changing them remounts the Explorer and clears progress. Progress is not persisted, sent to a server or synchronized; closing the Explorer discards it. Repository content is rendered as text rather than executed. AI-assisted explanations could be added later behind an explicit evidence and privacy boundary; no model or external service is used here.

## VS Code extension

The extension acquires files from one trusted local workspace folder with VS Code workspace APIs, respecting `files.exclude` and `search.exclude`, filtering dependencies and generated output, and rejecting symbolic links. It checks resolved paths against the selected folder before reading or opening files; concurrent filesystem changes can still race those checks. Acquisition is bounded to 1,000 files, 2 MiB each, 50 MiB total and 30 seconds. Skipped files and capped searches produce explicit partial diagnostics. A SHA-256 fingerprint over paths and contents identifies the local snapshot. No source is uploaded and repository code is never executed.

The extension host starts a cancellable, 30-second worker to run dependency analysis, UI-flow analysis and the learning-plan generator. The host reuses analysis by workspace and fingerprint, invalidates on relevant file changes, and rejects stale async results. Impact uses the existing bounded reverse traversal. The webview receives graph and evidence data rather than source text, uses `@codedna/graph-ui`, and asks the host to open validated snapshot paths at source locations. The CSP disallows remote connections and inline scripts; dynamic graph styles require inline styles. Incoming messages use a versioned allowlist, and learning progress is held only in memory for up to three snapshot identities. Large graphs require an explicit layout request. Manual VS Code UI verification remains outstanding.

## Security and deployment boundaries

See [security and privacy](security.md) for the threat model, acquisition limits, extension workspace safeguards and outstanding release blockers. GitHub acquisition's body timeout and per-process request caps supplement, but do not replace, a shared ingress limiter or isolated analysis workers. Local descriptor-based reads check containment and file identity, but do not eliminate filesystem races; source opening remains a separate VS Code operation. The extension caches at most three recent workspace analyses.

## Verification and release boundaries

Browser integration uses Playwright against a local Next.js development server with deterministic mocked acquisition responses and Next.js and React Router fixtures; adapter and worker tests exercise server logic separately. CI installs Chromium and runs the suite. The Extension Development Host smoke uses an isolated test profile and a bundled workspace fixture, checking activation, commands, trusted analysis, impact and refresh; it does not drive webview rendering or untrusted-host prompts. Additional protocol and untrusted-workspace unit tests do not replace manual host verification.

`pnpm benchmark` creates synthetic snapshots of 100, 500 and 2,000 route files and reports generation, analysis, impact and learning timings, process RSS and serialized graph size. It also reports two concurrent worker latencies for 100 and 500 files. The 2,000-file case is within core limits but exceeds the 1,000-file acquisition limit. It does not measure VS Code webview rendering, full HTTP acquisition, peak memory, or provide a performance baseline.

Production acquisition currently returns 503 because there is no verified shared limiter. The development-only worker limits V8 heap and execution time and is cancellable; worker threads share a process and do not form a security boundary. Public deployment still requires a trusted distributed rate/queue budget and process/container CPU and memory isolation, with no direct ingress bypass. The worker entry file and its dependencies must be included by any chosen deployment packaging; serverless/standalone deployments are not yet validated.

### Archive acquisition (local development)

The web acquisition route requests a commit-pinned gzip tarball from the fixed `codeload.github.com` host after retrieving GitHub metadata, commit and complete tree. It streams the archive without writing files, rejects unsafe or duplicate paths, and checks each included source file's size and Git blob SHA against the tree. Downloaded archives are limited to 100 MiB compressed, 200 MiB expanded and 100,000 entries; existing source snapshot limits still apply. Unsupported archive entries are not analyzed. GitHub archive export rules can omit files; such cases fail as incomplete rather than producing a misleading graph. The legacy blob acquisition strategy remains available to API callers. Live archive acquisition has not yet been verified because GitHub returned a rate-limit response during local testing. Production acquisition remains disabled until shared protections and isolated analysis are in place.

### Architecture overview

The Architecture Map groups analyzed files by their repository paths: monorepo `apps/<name>` and `packages/<name>` directories, other top-level directories, root files, and external packages. These are structural groups, not inferred architectural roles. An arrow represents one or more actual dependencies, directed from importer to dependency; dependencies within a group are counted separately. Selecting a group opens its files and directly connected neighbors using the original file-level edges and their source metadata. The All files view retains the complete graph. The overview preserves original edges as evidence in its adapter; unresolved imports and relationships outside the analyzer's supported language scope cannot be visualized as confirmed dependencies. Grouping alone does not infer application layers or runtime execution flow.

The Explorer file panel presents the snapshot as expandable directories, opens ancestors of a selected file, and offers back and forward navigation through selected Architecture Map nodes. The file inspector separates outgoing file dependencies, incoming dependents, and external packages with dependency kind and source location. External packages are hidden from the architecture map initially and can be shown; they remain available in the inspector. This organization describes static import evidence, not inferred runtime execution, architectural roles, or proof that a file accesses a database. GitHub acquisition excludes generated directories such as `.next` and `node_modules`.
